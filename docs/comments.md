# 评论与通知合同（Issue #14）

## 权限与公开线

- 已发布作品的评论/回复列表身份无关，游客可读；GET/HEAD 不读取或续期 session。点赞态和互动上下文单独走私有 no-store 端点。
- 新评论、回复、点赞和取消点赞要求当前 `canAccess`。回复/点赞与删除争用评论行锁；等待结束后重新查询发布状态并使用当前时间判定权益，不能复用等待前的判定。
- 删除是作者/管理员的数据撤回权。Issue 规则 3 列举的权益受限操作是评论/回复/点赞，规则 8 单独规定作者/管理员删除，因此权益过期、撤销或作品下线不影响撤回已有评论。GPT 6.1 第二轮评审已对照 Issue 原文接受此解释。
- 软删除隐藏正文与作者，保留已有回复的只读展开入口；新回复不能指向已删除目标。

## 分页与客户端并发

- 根评论按 `(like_count DESC, created_at DESC, id DESC)` 活排序，回复按 `(created_at ASC, id ASC)` 排序。
- 本地对根评论点赞/取消点赞后重载首页并重置游标。重载递增列表请求代次；旧分页和旧定位请求不能覆盖新条目/游标。去重仅防重复，不能保证其他用户并发改变排序时的跨页快照一致性。
- 通知锚点先加载所属根，再累积回复页；根与回复各最多加载 10 页。目标超出上界或请求失败时显示提示，保留普通翻页入口。展开状态在重载后保留，但首页之外的线程暂时不在 DOM，重新翻到该根时恢复。
- 点赞查询按评论分别记录读取/写入版本。查询发出后发生的本地互动，以及更晚的查询，不能被旧查询覆盖；同一评论的写请求互斥。
- 通知标记已读只在请求成功后更新，已读操作互斥但不阻塞分页；失败不回滚列表快照。全部已读成功后的旧通知分页应用已读覆盖，避免迟到的页返回旧状态。

## 时间精度与通知策略

- 评论与通知的 `created_at` 为 `timestamptz(3)`，默认值截断至毫秒，与 JS Date 游标精度一致。迁移 0007 将既有微秒时间截断至毫秒；原微秒部分不可恢复，如需回滚恢复精确时间，应使用迁移前备份。
- 评论、点赞记录/计数、通知在同一事务维护。通知事件键派生自 `reply:<commentId>` 或 `like:<commentId>:<actorId>`；同人对同评论取消后重赞不重复通知，以减少打扰。
- 取消点赞不撤销历史通知。通知投影仅联查已发布作品；作品下线时标题/链接为空，不泄露下线内容；重新发布后可恢复跳转。

验收证据见 `artifacts/comments-accept-*/`；HTTP 成功或 bundle 含相关逻辑不代替浏览器交互验收。
