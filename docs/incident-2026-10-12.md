# 2026-10-12 生产主机资源迟滞与恢复

所有时间为 Asia/Singapore。影响：约 15:58–16:15，API 与 SSH 严重迟滞，公开详情的权限门禁返回 503，不能回退到旧公开全文。数据库与 OSS 独立存储，没有执行删除、重置或迁移回滚。正式三篇文章尚未发布。

## 已确认与归因边界

主机为 2CPU/1GB，Linux 实际内存约 894MB，无 swap。sysstat 的 15:50 采样可用内存 327176KB；16:01 为 87556KB，16:11 为 74620KB。同期匿名页从约 302MB 增至 577MB，page-in 由约 6MB/s 升至 138MB/s，I/O 等待最终 76.65%，24–31 个任务阻塞。16:01 内存压力 60s 均值 89.92%，I/O 压力 97.36%。journald 从 15:58 起反复记录 `Under memory pressure, flushing caches`，logind 最后因 watchdog 超时退出。

这确认故障机制为内存压力下持续回收、代码/数据页反复读盘，导致全机 I/O 迟滞；未找到内核 OOM kill 记录，API 容器 OOMKilled=false。不能把故障描述为已确认 OOM、CPU 算力耗尽或数据库故障。

故障前同时执行两组生产验收，并通过无宿主机锁、无资源上限的入口创建 CLI 容器；15:57:28 的 `cache status` 与 15:57:30 的 `publish` 是直接记录的并发入口。它们与主机内存/进程数增长时间一致，是高度相关的触发负载。缺少故障时逐进程 RSS/分配记录，无法证明所有增长由某一个 CLI 或 API 进程产生。恢复后限额下 CLI 实测约 54–63MB，不能倒推旧故障峰值。

## 操作错误与恢复

在根因未确认时，执行了整机 StopInstance，随后追加 ForceStop；这是不恰当的恢复决策，扩大了不可用时间。停止期间实例长时间 Stopping。16:13 起 StartInstance 恢复，16:16 确认 SSH、API health 和匿名网页正文可读。今后不得未经用户明确授权停止、强制重启或释放实例；异常时先只读取诊断与资源指标，若无法诊断，报告证据及必要的外部操作。

## 预防与验证

`/opt/yoryon/blog` 在分配容器之前取得宿主机 singleton 锁（等待上限 120s），固定容器名，CLI 256MB/0.5CPU/64PID；保留数据库事务锁用于跨主机发布与 GC。所有发布、状态与恢复命令使用该入口，生产验收严格串行。并发等待不得预先分配容器。API/Caddy 原有资源上限不变。

本次没有增加 swap、扩容、停止系统服务或购买云产品。限额后缓存验收 22/22 通过，正常修改到真实页面验证约 10.3s，期间主机可用内存最低约 307MB。部署/权限/媒体回归以单独工件为准，不能仅以 health 成功确认整个业务恢复。
